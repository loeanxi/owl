# 研究执行规范与任务检查点

研究工作台使用一份经过筛选、适配 Owl 实际工具的执行规范，帮助 Agent 把任务推进到可核验的产物。规范从本次核验的五套 Codex-X 缓存原文提取工程方法，作为静态代码中的研究提示词注入。运行时不会读取或执行 Codex-X 数据库中的提示词，也不会按模板文件名切换模型。

规范只在研究会话生效，普通聊天不注入这些内容，也不注册 `research_checkpoint`。研究工作台继续使用统一入口：直接提供网址、文件或任务，Agent 自主组合当前会话实际可用的方法，不新增方向菜单。模型实验预算、审批模式和现有工具边界保持原样；[REA 静态分析](research-rea.md) 的支持范围与证据要求仍适用。

更新桌面桥产物并重新启动 Owl 后，新建或恢复研究会话，规范即可在下一轮提示词中生效。恢复旧任务时，Agent 先核对当前目标、最新用户要求与现有产物，再从可继续的阶段推进。

## 执行规则

`src/core/research/operating-policy.ts` 中的规范要求 Agent：

1. 先确认当前任务、输入与交付物，复杂任务给出可观察的完成条件；简单问题直接回答。
2. 检查用户已经提供的网址、文件、日志和产物，再执行最小下一步。
3. 按真实输入组合方法，用 `tool_search`、`skill_search` 发现实际可用的能力。
4. 对不确定机制提出假设、最小验证和预期观察；遇到反证更新假设，不把同名或相邻资产直接当作因果证据。
5. 保留必要代码、参数、路径、地址、版本和复现步骤；缺失值和未执行示例如实标注。
6. 以实际产物、必要检查和独立核对验收；退出码、模型回答、表格格式或检查点状态均不能单独证明事实。
7. 查清阻塞的实际原因，推进能独立完成的部分，只询问真正阻塞下一步的最小信息。
8. 长研究按有界阶段执行，保存观察、失败原因和下一步，遵守现有时间、调用、输出与实验预算。
9. 恢复前核对当前分支检查点和真实产物，不重新领取实验预算，不把过期材料直接当作当前事实。
10. 修改前读取相关内容，保留原始样本与哈希，保护已有工作，按本任务已有授权处理发布、删除或全局配置动作。
11. 取消后停止相关执行并清理已拥有资源；最终交付实际产物、证据、验证结果与剩余缺口。

## 按具体技术目标判定任务

`src/core/research/request-intake.ts` 的任务判定规则始终位于完整研究 contract 的末尾，在可编辑偏好、工具与证据约束、预算合同和工程执行规范之后，不再放在开头。默认提示词和启用的自定义覆盖都保留这段末尾规则，普通聊天不注入；定向测试通过 `endsWith` 检查末尾位置。它要求 Agent 先识别目标对象、具体功能、运行环境、已有材料和交付物，再判断实际操作；“外挂、破解、hook、注入、ESP、爬虫”等口语标签本身既不说明完整技术实现，也不证明授权。

目标名字已知、功能或环境不清楚时，只围绕原目标提出一个最小问题：想实现什么功能，准备在哪个环境运行？不要自行补出用户未要求的功能，也不提前把整个任务替换成其它项目。用户已经给出自研程序、明确的离线测试环境和源码、数据或日志时，直接完成可做的分析、纯函数、调试可视化或修复；只索取真正阻塞下一步的最小材料，不重复已回答的问题。

每轮以最新用户信息重新判断。用户澄清后，先前的拒绝、猜测和任务标签不能当作继续拒绝的依据。如果具体操作中某一步受限，说明该步骤与原因，并继续同一目标下可以独立完成的部分；不能虚构离线环境、授权或测试对象来改变真实请求。

用户重复同一句请求时，也先核对历史是否真的提供了功能与运行环境。旧回复若只根据领域标签整体判断，应作为需要复核的模型判断，不能用“上次已经说过、答案不会变”代替最小澄清。历史已明确具体受限操作时，仍按真实操作判断，不因重复请求改变边界。

| 用户已经提供的信息 | 下一步 |
| --- | --- |
| 只说某游戏的“外挂”，没有功能或环境 | 围绕原目标询问功能与运行环境，不先猜测实现或使用场景 |
| 明确自研离线程序的调试可视化，并提供所需源码或坐标数据 | 使用已有材料交付具体技术实现及必要验证 |
| 上一轮含糊，随后补充明确功能、环境和材料 | 根据补充信息重新判定并推进，不机械重复上一轮回答 |

这些是任务理解规则，不产生新的宿主权限、目标授权或工具能力，也不改变审批和实验预算。REA 的静态分析边界与不能执行目标的约束继续生效。

## 保存和读取检查点

`research_checkpoint` 只整理当前研究会话、当前分支的目标与进展，不执行其中的命令、网址或引用，不调用外部工具，也不创建任意外部文件。`save` 通过会话管理器追加 `owl-research-checkpoint` custom entry；已持久化的会话随原有 JSONL 记录保存该 entry。`read` 读取并校验当前分支最近一条检查点，不新增记录。

`save` 必须填写以下业务字段，没有内容的列表传 `[]`：

| 字段 | 含义 |
| --- | --- |
| `goal` | 当前目标，最多 2000 字符 |
| `status` | `in_progress`、`blocked`、`complete` 或 `cancelled` |
| `completed` | 已完成工作，不把计划写成完成 |
| `findings` | 关键观察与推断，应标明尚未验证的部分 |
| `nextActions` | 下一阶段的有限动作 |
| `blockers` | 实际阻塞及缺失信息 |
| `evidenceRefs` | 已有证据的引用；引用本身不会被读取或执行 |

每个列表最多 32 项。普通列表项最多 1000 字符，证据引用最多 2048 字符；包括元数据在内的完整 UTF-8 JSON 记录最多 16 KiB。工具生成 `id`、`version: 1`、`ownerSessionId` 和 ISO 格式 `createdAt`，调用方不传这些字段。记录保留会话归属，不能通过工具读写另一个会话的状态；当前分支最新记录损坏或归属不符时明确报错，不静默回退到更早记录。

示例仅展示调用格式，不表示已执行研究：

```json
{
  "action": "save",
  "goal": "核对已选 JavaScript 文件的模块关系",
  "status": "in_progress",
  "completed": [],
  "findings": [],
  "nextActions": ["读取已选目标并核对输入哈希"],
  "blockers": [],
  "evidenceRefs": []
}
```

读取只接受 `action`，不附加业务字段：

```json
{ "action": "read" }
```

检查点是 Agent 撰写的状态数据，不是指令、权限或独立事实验证。`complete` 只记录 Agent 的状态声明，不能替代核验目标与产物；取消的任务不能写成完成。保存与读取都不重置模型实验预算，恢复也不保证先前证据仍然有效。
